# OffSec Lab 企画書

## 1. 企画概要

### 1.1 プロジェクト名

**OffSec Lab**

### 1.2 企画コンセプト

OffSec Labは、脆弱性診断・ペネトレーションテストを**ゲーム感覚で実践的に学習するためのローカルCyber Range**である。

TryHackMeやHack The Boxのようなセキュリティ学習サービスを参考にしつつ、単なる知識問題や疑似的なハッキング操作ではなく、

- 実際のLinux
- 実際のネットワーク
- 実際のWebアプリケーション
- 実際のセキュリティツール
- 意図的に実装した脆弱性

を用いて、攻撃者視点で調査・分析・侵入・検証を行う体験を提供する。

OffSec Labの最大の特徴は、

**「ゲームを進めること」と「実務で使うセキュリティ技術を習得すること」を一致させる**

ことである。

---

# 2. 企画背景

脆弱性診断やペネトレーションテストの学習では、書籍や動画だけでは実践的な感覚を身につけにくい。

一方で、TryHackMeやHack The Boxなどのサービスでは実践的な演習が可能だが、

- 学習内容を自分の理解度に合わせて変更しにくい
- なぜその攻撃が成立するのかを十分理解せず攻略できる場合がある
- 攻撃だけでなく修正・再テストまで体験する機会が少ない
- 自分が理解したい技術構成を自由に追加できない

といった制約がある。

そこで、

**「自分自身が脆弱性診断を学ぶためのCyber Rangeを、自分自身で設計・開発する」**

というアプローチを採用する。

これにより、

1. Cyber Rangeを利用することでセキュリティ技術を学ぶ
2. Cyber Rangeを開発することでWeb・インフラ・ネットワーク技術を学ぶ
3. Cyber Rangeを診断することで脆弱性診断技術を学ぶ

という3つの学習を同時に実現する。

- Networking
- HTTP
- Web Application
- Python
- PHP
- JavaScript / TypeScript
- API
- Database
- Docker
- Git
- Testing
- System Design

を学習する。

---

## 3.3 ポートフォリオの作成

最終的には、セキュリティエンジニア・脆弱性診断エンジニアへの転職活動で提示可能な成果物とする。

単に、

「脆弱性のあるWebアプリを作った」

だけではなく、

**要件定義 → 設計 → 実装 → テスト → 脆弱性診断 → 修正 → 再テスト**

まで一貫して実施したプロジェクトとして完成させる。

# 5. プロダクトコンセプト

OffSec Labでは、

**「読む → 試す → 攻撃する → 理解する → 修正する」**

という学習サイクルを採用する。

基本的なChallengeの流れは以下とする。

```text
Mission Start
      ↓
Scenario確認
      ↓
Reconnaissance
      ↓
Enumeration
      ↓
Vulnerability Discovery
      ↓
Exploitation
      ↓
Flag / Objective達成
      ↓
脆弱性解説
      ↓
Remediation
      ↓
Retest
      ↓
Mission Complete
```

単純にFlagを取得して終わるのではなく、

**「なぜ攻撃できたのか」**

まで理解することをゴールとする。

# 9. AI Mentor

OffSec Labでは将来的にAI Mentorを搭載する。

AI Mentorは単純に正解を提示するものではない。

プレイヤーの行動履歴や現在の状況を基に、

**次に考えるべきことを提示する学習支援AI**

として設計する。

例：

プレイヤー：

```bash
nmap 10.10.0.5
```

結果：

```text
22/tcp
80/tcp
```

AI Mentor：

> 2つのサービスが見つかりました。
>
> Exploitを探す前に、それぞれのサービスの種類やバージョンを確認してみましょう。
>
> Nmapにはサービス検出機能があります。

# 10. Hint System

Hintは段階的に提供する。

## Hint Level 1

思考の方向性だけ提示する。

例：

> 対象ホストで利用可能なサービスを調べてみよう。

## Hint Level 2

使用する技術を提示する。

> Port Scanを利用してみよう。

## Hint Level 3

ツールを提示する。

> Nmapを利用してみよう。

## Hint Level 4

コマンド例を提示する。

```bash
nmap -sV TARGET
```

プレイヤーが自分で考える余地を残す。

# 14. セキュリティ設計方針

OffSec Labには意図的に脆弱なサービスを実装するため、Lab環境の隔離を重要要件とする。

原則：

- Internetへ脆弱なサービスを公開しない
- Docker内部ネットワークを利用する
- Host Port公開を最小限とする
- 本物の認証情報を使用しない
- Production環境へアクセスしない
- 実在するシステムをTargetにしない
- Challenge Containerを使い捨て可能にする
- Challenge終了後に初期状態へ戻せるようにする

---

# 15. 脆弱性Challenge設計方針

Challengeは単に攻撃可能な環境を用意するだけではない。

各Challengeには以下を定義する。

### Vulnerability

脆弱性名称。

### Scenario

どのような業務システムなのか。

### Vulnerable Code

問題となる実装。

### Root Cause

なぜ脆弱性が成立したか。

### Attack

どのように利用されるか。

### Impact

攻撃された場合の影響。

### Detection

診断時の発見方法。

### Remediation

修正方法。

### Retest

修正後の確認方法。

# 20. MVPの考え方

MVPでは、

**「TryHackMeのようなサイトを完成させること」**

を目的としない。

MVPのゴールは、

> OffSec Lab上で1つのMissionを選択し、隔離されたTargetを起動し、実際に調査を行い、Challengeを達成できること。

とする。

MVPではゲーム機能を必要以上に実装しない。

後回し候補：

- Multiplayer
- Ranking
- Friend
- SNS
- Achievement
- 課金
- Cloud Hosting
- Kubernetes
- 大規模Microservices

# 21. 成功基準

OffSec Lab v0.1の企画成功基準は以下とする。

### Product

最低1つのMissionを最初から最後までプレイ可能。

### Technical

実際のLinux・Docker・Networkを利用した演習が可能。

### Security

脆弱なTarget環境がHostおよびInternetから適切に隔離されている。

### Learning

Missionを通じて最低1つのセキュリティ技術を理解できる。

### Documentation

要件・設計・テスト内容が文書化されている。

### Portfolio

第三者へ、

「何を作り、なぜ作り、どのように設計・検証したか」

を説明可能。

**「脆弱性診断エンジニアになるための実践型セキュリティ学習ゲーム」**

を作ることである。

プレイヤーは単にFlagを取得するのではなく、

```text
Understand
↓
Investigate
↓
Exploit
↓
Explain
↓
Fix
↓
Retest
↓
Report
```

まで行う。

そしてOffSec Labそのものを開発する過程も含めて、

- Software Engineering
- Infrastructure
- Cybersecurity
- Vulnerability Assessment
- Penetration Testing
- AI Agent Development

を横断的に学習する。

**OffSec Labを完成させることと、開発者自身が脆弱性診断エンジニアとして成長することを同じプロジェクトとして扱う。**
